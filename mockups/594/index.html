Comment on a rendered Markdown file, and put it in the session

You read a plan the session wrote. You select a few words, click ✎ comment, type what to change, and the passage and your note land in that session's input box — just like a comment on a Changes hunk today. You press ⏎ there to send.

The box is the Changes one (CommentBox, cv-comment): same textarea, hint, Cancel and Put in session, same keys (⏎ puts it in, ⇧⏎ new line, Esc closes). Only its label and placeholder say "passage" instead of "hunk".

It docks at the bottom of the file, under the text, instead of opening inside the text as it does under a hunk. How a Claude Code tab shows it before you press ⏎

> [Pasted text #1 +6 lines]Make it 5 tries — the network on trains drops a lot.

How the comment names its place:

  • path:line (or path:first-last) — the lines in the file, counted the way an editor counts them.
  • the file's own lines in a fence — the Markdown source, not the rendered words. The agent can find them with a plain text search even if the file has moved on, because they are its exact text (bold marks, links and all).
  • Selected: the words you picked — only when they are part of those lines, so the agent knows which part you mean.

Which lines: the smallest block that holds the selection — one paragraph, one list item, one table row, one heading, one code block. A selection across several blocks takes all their lines.

Same shape as a hunk comment (path line, a fence, the note typed after it), so it reaches every agent the way a hunk comment already does.

Several comments: there is no pending-comments list in Changes today — each ✎ comment goes straight into the input box, unsent. Do it again and the next one lands after the first; one ⏎ sends them all. That several pastes in a row all wait is inferred, not checked: the ledgers measured one paste plus a note. The build checks it on every agent before it ships.

5 · How it fits PR #1585 (the faster Markdown preview)

PR #1585 (open) moves the Markdown render into a worker and draws the file in top-level blocks; on a reload, a block whose HTML did not change keeps its DOM. This design is built on top of it:

  • Line numbers come from markdown-it itself. Every block token (heading, paragraph, list item, table row, code block) carries its source lines (token.map; checked with the repo's markdown-it). A small rule in markdown/render.ts writes them on each block element as data-line.
  • Lines inside a block are counted from the block's start, and the start of each top-level block travels next to the block list (not inside its HTML). Why: if absolute line numbers sat in the HTML, adding one line at the top would change every block below, and #1585 would have to redraw the whole file on each edit — the slowness it removes.
  • The text the comment quotes is sliced from the same text the preview just read (local or over ssh), so path, line and quoted lines always agree with what is on screen.
  • An open box keeps what it points at (path, lines, quoted text) when you open it, like the hunk comment keeps its hunk; a reload while you type does not lose it. The mark is drawn again on the new block, or dropped if those lines are gone.

6 · Left out

  • A ✎ on every block on hover (no selection needed): fills the page with buttons while you read, and cannot point at a few words inside a paragraph.
  • A button in the file's top bar acting on the current selection: far from where your eyes are.
  • The Source and Diff views of a Markdown file, and other file types: the ask is the rendered plan. The same box could come there later.
  • Naming the place by heading only: two sections can share a heading, and the heading alone does not say which line.

7 · The one decision

Build it as shown above?

  1. Yes, as shown (recommended) — select → ✎ comment → box at the bottom → path:line + the file's own lines + your note, unsent in the input box; several comments simply pile up there. Cost: about 250 lines, plus e2e for all eight tab kinds; one small change to the render worker (needs #1585 merged first).
  2. Yes, but name the place by the nearest heading and the selected words only (no line numbers) — no change to the render worker. Cost: the agent has to search; the rendered words often do not match the file (bold marks, links), and the same words can appear twice.
  3. Yes, and add a pending-comments list in the Workbench with "Send all" — comments wait in Koloft, not in the input box. Cost: a new list and its state per tab (and one for Changes to match), roughly double the work; the input box already lets several comments wait.
  4. Don't build it — close the issue. Cost: you keep copying passages into the terminal by hand.
