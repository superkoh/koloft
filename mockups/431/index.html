#431：远程会话的开发服务器，直接在 Workbench 网页标签里打开

现在：远程会话（ssh 连到另一台机器）里，agent 在那台机器上跑了 npm run dev，服务开在那台机器的 5173 端口。可 Workbench 的网页标签在这台 Mac 上，打开 localhost:5173 找的是Mac 自己的 5173，看不到那台机器的页面。

做了以后：远程会话的网页标签里，localhost:<端口> 指的就是那台机器的端口。Koloft 在已经连着那台机器的那条 ssh 连接上加一个"端口转发"，不用重新登录，页面直接出来。

一、探查结果（Docker ssh 实验室，2026-10-30）

  • 在 Koloft 共用的那条 ssh 连接上执行 ssh -O forward -L 127.0.0.1:<Mac端口>:localhost:<机器端口>： 马上成功（约 5–15 毫秒），没有新的登录，其他命令照常走这条连接；页面在 Mac 上用 127.0.0.1 和 localhost 都打得开，30 个请求同时发也都成功。
  • ssh -O cancel -L 同样的写法 能撤掉；写法差一点（比如少了 127.0.0.1:）就撤不掉，而且照样返回成功。
  • Mac 端口必须 Koloft 自己挑：-L 不接受 0（不像 -R 会自己挑一个）。
  • Mac 端口已被别的程序占用 → 失败（退出码 255），换一个端口即可，连接不受影响。
  • 机器上那个端口没人在听，或者那台机器的 sshd 关了转发（AllowTcpForwarding no）→ 加转发时照样"成功"， 真打开页面时连接被重置。两种情况从 Mac 这边分不出来。
  • ssh 连接退出（-O exit），转发也跟着没了；连接还没起来时加转发会失败。

脚本和完整输出：notes/431/；事实写进了 docs/platform-contract.md §33。经过跳板机（ProxyJump）这条路没测，推断一样。

二、推荐做法（A）：自动转发，什么都不用填

agent 在 kt-key 上跑 npm run dev（端口 5173）
        │
        ├─ agent 执行 open http://localhost:5173      （#192 / PR #1265 让这句能到 Workbench）
        ├─ 或者你在这个会话的网页标签地址栏输入 localhost:5173
        └─ 或者 agent 用 playwright-cli 打开它
        ▼
Koloft 看到：这是远程会话的网页标签 + 地址是 localhost / 127.0.0.1 / [::1]
        ▼
在 kt-key 那条已有的 ssh 连接上加转发：Mac 5173 → kt-key 5173
（Mac 的 5173 被占了，就换一个空闲端口，页面地址跟着换）
        ▼
网页标签显示 kt-key 上的页面；地址栏旁边显示机器名 "kt-key"
  • 你看到的：地址栏还是 http://localhost:5173/，旁边多一个和左边栏一样的机器名小标签 "kt-key"（绿点 = 连着）。鼠标停上去说明"这是 kt-key 的 5173，经 ssh 转到这台 Mac"。
  • 端口号尽量不变：Mac 上 5173 空着就用 5173，这样页面里写死的 localhost:5173（热更新、接口）都照常工作。被占了才换号，换号时地址栏显示真实的新号。
  • 换号的坏处（照实说）：换了号以后，页面里写死 localhost:5173 的接口和热更新可能坏（换号等于换了"网站"，开发服务器一般不允许跨站请求；热更新的 websocket 能不能被改写还没测）。这时的办法只有一个：关掉 Mac 上占着 5173 的程序再刷新。两台机器都要 5173 时，第二台就是这种换号情况。Koloft 自己分出去的 Mac 端口会认出来直接放行，不会再当成机器端口转一次。
  • 页面里再访问别的 localhost 端口（比如接口在 3000）：同样自动转发到那台机器的 3000。
  • 转发期间整台 Mac 都看得到：转发开在 Mac 的 127.0.0.1:5173 上，这期间 Mac 上任何程序（你自己的 Chrome、本机会话的网页标签）打开 localhost:5173 看到的都是那台机器的页面；本机这时再起 npm run dev 会发现 5173 被占而改用 5174。撤掉转发后恢复。
  • 什么时候撤：这台机器上没有网页标签再用这个端口、会话关掉、或 Koloft 退出时撤掉（Koloft 的 ssh 连接在退出后还会留着，所以退出时必须主动撤，不然 Mac 端口一直被占）。像现有的远程浏览器控制一样，把加过的转发记到文件里，Koloft 崩溃后重开时也能撤掉。
  • 连接换了怎么办：每次要用转发前先问一下连接（-O check，约几毫秒）；连接换了（进程号变了）就重新加。刚恢复会话、连接还没起来时，页面先显示"打不开"，点 Retry 即可。
  • 打不开时：用现有的"打不开"页面，下面多一行说明可能的两种原因。
  • 和现有围栏的关系：现在只有"被机器上的 playwright-cli 驾驭"的网页标签受限，它碰不到 Mac 的任何地址（localhost、Mac 的网卡 IP、解析到 Mac 的域名）。做了以后，远程会话的所有网页标签里，localhost / 127.0.0.1 / [::1] 一律指那台机器（驾驭的标签打开它得到机器上的服务，不再被拒）；Mac 的网卡 IP 和解析到 Mac 的域名，对驾驭的标签照样拒绝。

四、要你选的（推荐 A）

选项 你会怎么用 代价
A 自动转发（推荐） 什么都不用做：agent 说"页面在 localhost:5173"，打开就是对的。地址栏输入、agent 的 open、playwright-cli 都一样。 改动约 250 行（推断，没数过）。远程会话的网页标签里再也打不开 Mac 自己的 localhost（要看 Mac 上的服务，用本机会话的标签）。转发期间 Mac 上所有程序打开 localhost:5173 都看到机器的页面。Mac 上同号被占时换号，页面写死端口的部分可能坏。
B 手动填端口 Workbench 的 "+" 菜单里加一项 "Forward a port…"，你输入 5173，才转发并打开。 约 150 行（推断）。agent 自己打开的 localhost:5173 还是会打到 Mac 上，看到错的页面或打不开；每次都要你手动填。
C 等 #224 一起做 先做 #224（"+" 菜单列出会话正在听的端口），远程会话也列出机器上的端口，点一下转发并打开。 最大、最慢：#224 已拍板，有分支 feat/224-session-ports（只有界面稿）、没有 PR；而且只解决"点菜单"这一条路，地址栏和 agent 打开的问题还在，最后还得做 A。

端口从哪来：A 不需要输入也不需要发现——端口就是地址里写的那个。#224 以后加"列出端口"时，远程会话的那几行点下去走的就是 A 这条路，不用另做。

五、8 种会话标签页

标签页 怎样

六、老用户升级后

不存任何新设置。升级前已经打开的远程网页标签，地址是 localhost:… 的，刷新后就指向那台机器（以前它指 Mac，本来就是错的）。地址栏的历史记录照旧按工作区记，不受影响。本机会话完全不变。

七、大概改哪里

  • 新的 src/main/remote/portForward.ts：按机器记"机器端口 → Mac 端口"，用现有的 runMasterCommand 发 -O forward/-O cancel，退出时用 masterCommandOutlivingKoloft 撤，ssh 连接换了（进程号变了）就重新加，和 browserTunnel.ts 管 -R 的做法一样。
  • 网页标签的请求在 index.ts 已有的 ses.webRequest.onBeforeRequest 里拦：属于远程会话的网页、地址是 localhost → 先确保转发，端口号不同就改写地址。
  • 地址栏 BrowserAddressBar.tsx 加机器名小标签；打不开页面 WorkbenchWebGuests.tsx 加一行说明。
  • 测试：Docker 实验室加一个用例——机器上起一个小服务，远程会话网页标签打开 localhost:端口 看到内容，关掉标签后转发撤掉。

八、还没查的（开工时先查）

  • 经跳板机（ProxyJump）的连接上加 -L：推断和直连一样，没测。
  • onBeforeRequest 里等转发加好再放行、以及改写 websocket（热更新）地址：没测。
  • Codex 沙箱里起的服务能否监听：没测。
  • 新开的网页标签认对会话：main 靠渲染层在网页挂上后报告"这个网页属于哪个会话"，报告到之前查不到就会当成当前选中的会话。后台远程会话里 agent 打开的新标签，第一个请求有可能被当成选中的（本机）会话——推断，没测。开工时先测，必要时让打开请求自己带上会话，不靠"当前选中"。
