#758 · A folder you add shows its past sessions in the middle panel

Today: you add a folder you already worked in, and the app shows nothing about that work. After: the middle panel lists it, one click to carry on.

Every frame below is the real app's page and stylesheet, captured from a build of main; only the middle panel (and, in option B, the sidebar rows) was changed by hand. Words in the frames are the app's own English.

What is still broken

The welcome's own path is already fixed: since the new welcome, the folders it pins bring their last sessions into the sidebar (test T-OB-02). What is left is every folder added by hand (⇧⌘O, the folder button, a remote directory): the sidebar and the panel stay empty, and the past sessions sit behind the folder menu's "Restore session…". A probe on main shows it (notes/758/probe-758.spec.ts).

Option A · list them in the panel suggested

When a folder has no row of its own in the sidebar but has past sessions, the panel shows a "Past sessions" block under the buttons: the newest three, each with its branch and age, as the Restore dialog words them. Clicking one does what the dialog does: the session resumes and its row joins the sidebar, and the block is gone (the folder now has a row). With more than three, a last row opens the Restore dialog with all of them. The sidebar stays as it is. This is what the issue asks for.

Cost: the panel reads the Restore list once each time such a folder is picked, and again when its sidebar rows change. That read waits for every agent's answer, so the block comes a moment after the buttons. A read made by the panel never raises the "history could not be read" toast; an agent that cannot answer is just left out.

Option B · adding a folder brings its last sessions into the sidebar

No new block. Adding a folder by hand does what the welcome does: up to four sessions from the last two weeks become grey rows in the sidebar, and today's "Recent" block lists them. Older sessions stay behind "Restore session…". Folders that are already pinned do not change.

Cost: the sidebar fills by itself, which the issue asked not to do. A folder that was removed and is added again gets back sessions the user had taken off its list. Sessions older than two weeks are still hidden.

Option C · one "Restore session…" button

Under the buttons, a "Restore session…" button, shown for every folder whose menu item is enabled today; it opens the dialog that exists today. The smallest change: nothing new is read. The sessions' names are still one click away, and there is no count (a count would need the same read as option A).

What each kind of folder and agent does (option A)

The block reads the same list the Restore dialog reads, so the two always agree. The panel and its buttons show at once; the block comes when every agent has answered, which can take about 10 seconds when a remote machine is out of reach. The block and option C's button show for the same folders that have "Restore session…" enabled today.

After an upgrade

What sits behind "Restore session…" is every session that left the folder's list: ones from a plain terminal, and also ones ended by /clear, /exit, a closed tab or "Remove from list". A: a pinned folder shows the block only while its sidebar list is empty, so folders in use look as they do today. C: every pinned folder with such sessions gets the button. B: nothing changes for folders already pinned. In all three nothing moves by itself in an existing sidebar and nothing is lost.
